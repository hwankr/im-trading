# 수동 운영 절차와 전달 양식

버전: 0.3, 갱신일: 2026-09-08. 운영 방식은 **AI가 투자 판단·주문 지시·성과 기록을 맡고, 사용자가 계좌 조회·주문 입력·결과 전달을 맡는 것**이다. 사용자는 장중 요청에 맞춰 수시 대응할 수 있다. 실제 응답 시간은 운영하며 측정한다. 사용자 요청에 따라 같은 대화의 시장 점검 예약을 등록했으며, 등록 확인과 실제 자동 실행 성공은 구별한다.

API 연결은 필요하지 않다. 사용자에게 투자 전망이나 선호 종목을 묻지 않는다. 아래는 운영 절차이며, 실제 자료 접수·판단·주문 진행 상태는 프로젝트 README와 로컬 실행 기록에서 확인한다.

## 1. 한 번의 운영 흐름

| 순서 | 담당 | 수행 내용 |
| --- | --- | --- |
| 1 | 사용자 | 모의계좌 잔고·현금·미체결·최근 주문 결과와 확인 시각 전달 |
| 2 | AI | 자료 정리, 시장 조사, 규칙·위험 검토, 매매 또는 보류 결정 |
| 3 | AI | 가격·수량·입력 기한·미체결 처리 조건이 명확한 지시서 발행 |
| 4 | 사용자 | 지시된 조건과 기한 안에서 앱 입력, 접수 결과 전달 |
| 5 | 사용자 | 체결·미체결·거절·취소 결과를 앱에서 확인해 전달 |
| 6 | AI | 실제 체결과 잔고를 대조하고 다음 판단 또는 추가 확인 요청 |

조회와 지시대로 입력한 작업은 `operational_assistance`로 기록한다. 사용자가 투자 전망에 따라 종목·가격·수량·시점을 바꾸면 `investment_intervention`으로 기록한다. 단순 오입력과 대응 불가는 운영 오류·지연으로 분류하고 결과 손익에 미친 영향을 보존한다.

## 2. 계좌 상태 전달

앱 화면 캡처나 아래 텍스트 양식을 사용할 수 있다. 캡처라면 AI가 값을 정리하고 읽히지 않는 필수 항목만 추가로 요청한다. 이름·계좌번호 대신 `paper-main` 같은 가명을 사용한다. 비밀번호·인증 정보는 전달 양식에 포함하지 않는다.

### 첫 실행과 주문 검토에 필요한 정보

```text
[계좌 보고]
화면 확인 시각(KST):
계좌 가명 / 모의투자·대회 그룹 확인:
예수금·현금: [앱의 항목명과 값]
현금 주문가능금액:
총평가금액 / 공식 수익률: [표시되면 기재]

전체 보유종목:
- 종목명 / 코드 / 보유수량 / 매도가능수량 / 평균매입가 / 평가금액
- 보유가 없으면 '보유 없음'

미체결 주문:
- 앱 주문번호 / 종목 / 매수·매도 / 지정가·시장가 / 주문가격
  / 원주문수량 / 누적체결수량 / 미체결잔량
- 확인 결과 없으면 '미체결 없음'

이전 보고 이후 주문·체결·정정·취소:
- 앱 내역과 시각 또는 '추가 내역 없음'
- 첫 보고라면 대회에서 이미 거래했는지 기재
```

공식 회전율, 인정 종목 수, 거래일수, 순위는 최초 보고와 장 마감 후 갱신한다. 매번 같은 화면을 요구하지 않고 관련 상태가 바뀌었거나 판단에 필요할 때 추가 확인한다. 여러 화면의 확인 시각이 다르면 각 시각을 보존한다.

빈칸·읽히지 않는 값은 `unknown`이다. 0원, 보유 없음, 미체결 없음으로 채우지 않는다. 예수금과 현금 주문가능금액을 같은 값으로 가정하지 않는다. 전체 계좌 범위를 받으며 관심 종목만 골라 전달받지 않는다.

주식잔고 탭의 총평가금액은 보유 주식 평가액으로 분류하고 현금 포함 전체 계좌 자산으로 대체하지 않는다. 그 화면의 평가손익률도 대회 중계실 수익률과 구분한다. 기기 시계에 시·분만 보이면 캡처 날짜·초·계좌 갱신 시각을 관측 사실로 만들어 넣지 않는다.

AI는 `report_id`, 화면 확인 시각 `observed_at`, 수신 시각 `received_at`, 실제 사용 가능 시각 `available_at`, 자료 형식, 파싱한 값과 불확실성을 저장한다. 사용자가 옮긴 값은 `user_transcription`, 캡처 판독은 `screenshot_read`로 구별하고 직접 API에서 조회했다고 표시하지 않는다.

예약으로 시장을 조회해도 계좌 보고는 새로 관측된 것이 아니다. 매 거래일 첫 판단에 그날 계좌 확인이 없으면 필요한 계좌 자료를 한 번 요청한다. 같은 날 초기 빈 계좌의 조건부 이어 사용은 저장된 정책 범위 안에서만 허용하며, 필요한 확인 없이 신규 주문을 허용하지 않는다. 이미 요청한 결손은 새 사실이나 시한 도래가 없으면 반복 알리지 않는다.

## 3. AI가 발행하는 주문 지시서

아래는 빈 양식이다. 실제 주문에는 AI가 모든 필수 값과 정확한 KST 시각을 채운다. 지시서마다 식별자를 발급하고 `검토 초안`과 `입력용 지시`를 구별한다.

```text
[입력용 지시]
지시서 ID / 결정 ID / 기준 계좌 보고 ID:
작업: 신규 / 정정 / 취소
대상: paper-main / 해당 대회 모의계좌
종목명 / 코드:
매수·매도:
주문 유형 / 지정가(원) / 수량(주):
원주문번호: [정정·취소 시 필수]
정정·취소 대상 잔량: [해당 시 기재]

입력 시작 조건:
입력 마감 시각(KST):
입력하지 않을 조건:
선행 주문·체결 확인 조건: [의존 관계가 있으면 기재]
접수 후 미체결 확인 시각(KST):
미체결 처리 지시: [잔량 유지·취소 및 적용 조건]

판단 근거와 주요 반증 조건:
입력 후 보고할 내용: 앱 주문번호·접수 시각·접수 결과
```

초기 AI 운영 정책은 **지정가를 기본**으로 한다. 이는 수동 입력 지연에도 주문 가격이 명확하도록 정한 설계이며, 대회에서 시장가를 금지한다는 뜻은 아니다. 다른 주문 유형을 쓰려면 AI가 그 이유와 실행 조건을 명시한다.

신규 주문 가격 판단에는 시장시각이 확인된 120초 이내 KRX 시세를 사용한다. NXT·통합 시세를 섞지 않으며 종목 제한, 최신 계좌 상태의 유효성, 종목별 앱 주문가능수량을 따로 확인한다. 예약 점검에 사용한 자료가 이 조건을 통과하지 못하면 그 자료로 입력용 지시를 발행하지 않는다.

사용자에게 '적당한 가격에 매수', '흐름을 봐서 매도', '남은 돈만큼 구매'처럼 투자 판단을 넘기는 지시를 내리지 않는다. 가격이나 상황이 지시 조건을 벗어나면 사용자는 임의 변경 없이 미입력 사유와 최신 상태를 전달하고 AI가 새 결정을 만든다.

**입력 기한은 아직 입력하지 않은 지시의 유효 시간이다. 이미 접수된 주문을 자동 취소하지 않는다.** 미체결 주문의 확인 시각·취소 계획을 별도로 적고, 사용자가 직접 앱에서 취소했는지 확인한다. AI가 계속 감시하거나 자동 손절·자동 취소한다고 표현하지 않는다.

## 4. 결과 보고

```text
[주문 결과]
지시서 ID / 앱 주문번호:
실제 입력 시각(KST):
상태: 미입력 / 접수 / 일부체결 / 전량체결 / 거절 / 취소확인 / 상태불명
확인 시각(KST):
실제 입력한 종목·방향·유형·가격·수량:
누적 체결수량 / 평균체결가 / 미체결잔량:
개별 체결시각·가격·수량: [확인 가능하면 기재]
수수료·세금: [표시되면 기재, 없으면 미확인]
변경·미입력·거절 사유:
갱신된 현금·보유·미체결: [필요한 화면이나 값]
```

접수 보고는 체결 보고와 다르다. '주문했음'이라는 메시지만으로 보유 수량·성과를 늘리지 않는다. 보고가 누락되면 `AWAITING_REPORT`로 남기며 미입력이나 미체결로 단정하지 않는다. 앱에서 주문 상태를 확인할 수 없다면 `UNKNOWN`으로 기록한다.

누적 체결수량의 반복 보고는 같은 수량을 다시 매수한 것으로 합산하지 않는다. 앱 주문번호·체결번호가 있으면 우선 사용하고, 번호가 없거나 다른 보고와 충돌하면 미확정으로 남긴 뒤 필요한 내역을 요청한다. 실제 개별 체결시각이 보이지 않으면 보고 확인 시각을 체결시각으로 대체하지 않는다.

## 5. 중복·부분 체결·기한 처리

- 결과가 오기 전 같은 주문을 다시 입력하도록 요청하지 않는다. 먼저 사용자의 앱 주문내역을 받는다.
- 한 번에 입력할 지시 묶음 하나를 활성화한다. 기존 상태 확인·취소 지시는 낼 수 있지만, 상태가 불명확한 주문과 충돌할 새 주문은 발행하지 않는다.
- 예약 호출과 사용자 요청이 겹치면 시작 시 최신 실행·결정·활성 지시·결과 보고를 확인하고, 이미 처리 중이거나 같은 스냅샷의 결정이 있으면 중복 판단·발행을 하지 않는다. 발행 직전에도 상태를 다시 확인한다. 이는 운영 절차이며 소프트웨어 잠금이나 자동 검증 프로그램의 구현 완료를 뜻하지 않는다.
- 매도대금 또는 체결 결과가 필요한 후속 매수는 실제 체결·현금 보고 이후 판단한다. 사용자가 체결을 예측해 다음 주문을 진행하지 않도록 의존 관계를 적는다.
- 일부 체결 뒤 취소되면 체결분은 보유·현금에 반영하고 나머지 취소만 기록한다. 취소 요청 중 체결될 수도 있으므로 최종 누적 체결수량을 다시 확인한다.
- 아직 입력하지 않은 지시를 바꾸면 이전 지시를 `SUPERSEDED`로 표시한다. 사용자가 이미 입력했다면 앱의 원주문번호를 기준으로 별도 정정·취소 지시가 필요하다.
- 입력 마감이 지났으면 미입력 지시는 만료된다. 이미 접수된 주문의 상태는 유지하고 별도 취소 계획을 따른다.
- 사용자가 대응할 수 없으면 그 사실과 시각을 기록한다. AI는 대응 가능 시점에 맞는 새 계획을 세우며, 지시를 실행한 것으로 가정하지 않는다.

## 6. 판단 주기와 평가

매 최종 판단은 매매·HOLD·BLOCKED 여부와 관계없이 다음 점검 방식을 기록한다. **예약이 비활성인 수동 모드**에서는 사용자가 다음 판단을 요청할 정확한 날짜·시각(KST), 요청 문구와 필요한 계좌·주문 자료를 적는다. **예약 활성 모드**에서는 다음 예정 자동 점검 날짜·시각(KST)을 기록하며, 사용자 조치가 필요할 때만 별도의 응답 요청 시각·문구·자료를 제시한다. 변화 없는 HOLD는 원본과 블로그 기록을 남기고 매번 사용자 재요청이나 알림을 만들지 않는다.

입력할 지시, 의미 있는 판단 변화, 새롭거나 심화된 위험, 조사 실패, 필요한 사용자 조치가 생기면 이 대화에서 알린다. 이미 알린 문제는 새 사실이나 시한 도래가 없으면 반복하지 않는다. 자료가 부족하면 BLOCKED를 유지하며 예약 시각이 왔다는 이유로 주문을 허용하지 않는다.

예정 점검·응답 요청 시각은 판단 완료나 주문 발행을 보장하는 시각이 아니다. 신규 주문 입력 마감, 미체결 확인·취소 시각은 각각 별도로 적고 주문이 없으면 해당 없음을 표시한다. 이미 지난 예정 시각을 다음 시각으로 안내하지 않는다. 실행이나 응답을 놓치면 다시 진행하는 시점의 최신 자료로 판단하고 이전 매수안·만료 지시를 재사용하지 않는다. 이미 접수된 주문은 기존 확인·취소 계획과 실제 결과 보고를 먼저 처리한다.

사용자에게 행동 안내를 보낼 때 다음 항목을 모드에 맞춰 구성한다.

```text
다음 점검: [예약 활성: 예정 자동 점검 YYYY-MM-DD HH:MM KST / 수동: 판단 요청 YYYY-MM-DD HH:MM KST]
사용자 응답 요청: [필요한 경우에만 정확한 KST 시각·요청 문구]
함께 전달할 자료: [필요한 계좌·주문 변화 또는 사용자 조치 없음]
주문 입력 마감 / 미체결 확인·취소: [주문이 있으면 각각의 정확한 시각, 없으면 해당 없음]
놓쳤을 때: 가능한 시점에 다시 요청. 최신 자료와 기존 주문 상태부터 확인.
```
